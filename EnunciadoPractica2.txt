Preámbulo

---------

El objetivo de esta segunda fase (Release 2) es que los estudiantes implementen, dentro de los principios de arquitectura SOA (Service Oriented Architecture), la tecnología de comunicación basada en servicios REST, además de integrar aspectos fundamentales de seguridad vistos en teoría.



Para ello, se consumirán APIs REST de terceros (información meteorológica) y se desarrollará y expondrá una API REST propia desde el backend para ser consumida por un frontend web y otros módulos del sistema. Adicionalmente, se implementarán tres pilares de seguridad: cifrado de canal, autenticación segura y principios de auditoría. Se partirá del sistema base desarrollado en la Release 1 de la red Water Management.

Especificación

--------------



Descripción funcional:

La funcionalidad base será idéntica a la implementada en la Release 1, incorporando las siguientes ampliaciones:



1- Nuevo módulo meteorológico (WM_W - Weather Control Office): Determinará la viabilidad de regar en las zonas donde se ubican las estaciones de riego (WS). Se comunicará vía API con un proveedor externo (OpenWeather) para suspender el riego si llueve o hay heladas.

2- Nuevo módulo de registro (WM_Registry): Permitirá a las estaciones de riego (WS) darse de alta o baja en el sistema mediante una API REST, obteniendo de forma segura sus credenciales de acceso.

3- Módulo Web (Front): Se creará una aplicación web pública que consumirá una nueva API (API_Central) para mostrar el panel de control (Dashboard) de la CENTRAL desde cualquier navegador.



Mecanismos de Seguridad:

* Autenticación segura: Canal cifrado para la comunicación entre los WS y el WM_Registry.

* Cifrado de datos: Cifrado simétrico de los mensajes intercambiados a través de sockets o colas entre la Central y los WS.

* Auditoría: Registro estructurado de eventos de seguridad y operacionales en la Central.

Registry (WM_Registry) - [Core System]:

WM_Registry será el módulo mediante el cual las estaciones desde WM_WS_M (Monitor) pueden darse de alta o baja en el sistema. Dispondrá de las opciones de alta, baja y autenticación de una WS. Las WS, previo a su autenticación y posterior prestación de servicios, deberán realizar una petición de alta para registrar su ID y localización. Sin este proceso no podrán autenticarse; ante un intento sin registro, recibirán una denegación de WM_Central.

* El mecanismo se realizará mediante un API_Rest que implementará los métodos oportunos (GET, PUT, DELETE, ...).

* La comunicación entre WM_Registry y WM_WS_M deberá realizarse mediante el establecimiento de un canal seguro (HTTPS, SSL, RSA, ...).

  - Opcional: La identificación de las WS podrá realizarse en base a un certificado (autofirmado) que contenga los datos identificativos.

* En respuesta al registro, WM_Registry devolverá las claves (credenciales) que la WS deberá usar durante su autenticación en WM_Central.

CENTRAL (WM_Central):

Será idéntico al ya realizado en la primera parte con las siguientes modificaciones:



1. Consumo de API_Rest de WM_W: WM_Central expondrá una interfaz (API) para que el módulo WM_W le informe si la localización de una WS tiene una climatología adecuada (sin temperaturas de congelación o lluvia). Ante una alerta, WM_W notificará a WM_Central.

2. Autenticación entre WM_Central y las WS: Las WS deberán autenticarse en WM_Central con las credenciales proporcionadas por el Registry. Si la autenticación se resuelve con éxito, la central devolverá a WM_WS_M la clave de cifrado simétrico ÚNICA POR WS que deberá ser usada para el cifrado de todos los mensajes enviados a la Central.

   - Estas claves podrán ser revocadas por WM_Central ante una supuesta vulnerabilidad. Se implementará una opción en la Central para restaurar claves. Al pulsarla, se borrarán las claves de una WS específica, la cual quedará fuera de servicio. Esto obligará a WM_WS_M a realizar una nueva autenticación mediante una opción incorporada en el mismo para obtener sus nuevas claves.

   - Opcional: Aunque la autenticación sigue siendo por sockets, el alumno podrá implementar un API Rest entre WS y Central a tal propósito.

3. Cifrado en el canal entre WM_Central y las WS (Engine): Se establecerá un sistema de cifrado simétrico (elegible y justificado por el estudiante) en el canal de colas o sockets para evitar ataques MITM (Man In The Middle). Todos los mensajes estarán cifrados.

   - Nota opcional: Kafka dispone de 3 componentes de seguridad (Cifrado SSL/TLS, Autenticación SSL/SASL y Autorización ACL). Su incorporación será valorada positivamente.

4. Registro de Auditoría: Se implementará un log de todos los eventos de forma estructurada:

   - Fecha y hora del evento.

   - Quién y desde dónde se produce el evento (IP de la WS, IP del operario FO).

   - Qué acción se realiza: Autenticaciones fallidas/exitosas, incidencias (fugas), cambio de situación de la WS, bloqueos, errores, etc.

   - Parámetros o descripción del evento.



API_Central:

Este componente expondrá un API_Rest (GET, PUT, DELETE, ...) que permitirá consultar el estado de los operarios (FO), las WS y los riegos en curso. Permitirá también ser consumido por WM_W para notificar situaciones de alerta climática o su cancelación.



Monitor (WM_WS_M):

Implementará una nueva opción (disponible en un menú) para conectarse a WM_Registry, registrarse de forma segura y recibir su clave de autenticación. La conexión y autenticación deberá realizarse de forma segura evitando la exposición en claro de los datos de identificación del CP. Durante la autenticación posterior con la Central, recibirá la clave para el cifrado simétrico que el WM_WS_E (Engine) deberá usar.



Weather Control Office (WM_W):

Determinará la viabilidad de operación de una WS en función al clima de su localización.



--------------------------------------------------------------------------------

[Página 5]



* Mediante una opción de menú o un archivo, se podrán introducir/modificar manualmente las ciudades donde se encuentran las WS a efectos de simulación en tiempo real sin reiniciar el sistema.

* Cada 4 segundos, se conectará a OPENWEATHER para consultar el clima.

* Si la temperatura baja de 0ºC (o llueve), notificará la alerta a WM_Central vía API_Central. La Central enviará un mensaje de parada a la WS. Si se está realizando un riego, el mismo finalizará con normalidad y posteriormente la WS pasará a modo "fuera de servicio".

* Cuando el clima vuelva a ser favorable, WM_W notificará la cancelación de la alerta y la WS se restaurará.



Nota: A efectos de la corrección, cualquier localización podrá ser cambiada a voluntad del profesor en cualquier momento mediante la opción de menú mencionada, sin necesidad de reiniciar ninguna parte del sistema.



Front:

Consistirá en una simple página web que, haciendo peticiones al API_Central, muestre el cuadro de monitorización de la Central. Debe visualizar claramente el estado de las WS (registro, activación, token), operarios, mensajes de error, mensajes de WM_W, clima y alertas. Nota: Se recomienda, por su sencillez, el uso de Node.js.



Field Operators (WM_FO):

No cambian su funcionalidad respecto de la entrega anterior. No es necesario que implementen mecanismos de cifrado con la Central.



Servidor de Clima (OPEN WEATHER):

Se utilizará la plataforma Open Weather (https://openweathermap.org/). El WM_W solicitará el API key gratuito y consultará el endpoint Current weather data para cada ciudad. Del JSON de respuesta provisto, el sistema analizará la temperatura ("main": {"temp": ...}) u otras condiciones adversas.

Para ello bastará con que el estudiante se registre en la versión FREE, solicite el API key (Get API Key) y realizar una petición para cada ciudad que quiera consultar.
